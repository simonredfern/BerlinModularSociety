# berlinmodularsociety.com

The site for the **Berlin Modular Society** — live modular music events in Berlin.

Static SvelteKit. Migrated off Notion + Super.so in September 2026, the same way
[3pi.tv](https://3pi.tv) was.

## Why it moved

Super rendered the Notion pages, but gave headings ids like
`id="block-293a7c7350e6802aab17da71dfcbba24"` — the raw Notion block UUID. Unguessable,
meaningless, and it changes if the block is recreated, so a section could never be
linked to. Here every event has a readable anchor — `/event-archive#bms53` — and every
heading carries a visible-on-hover anchor link.

The bigger win is that events stopped being prose. On the Super site the same event was
typed out in three places, and the three disagreed: the homepage's "Next Event" heading,
the `/upcoming-dates` table, and `/event-archive`. `/upcoming-dates` still listed BMS57
and BMS58 as upcoming months after both had happened. All three now read
`src/lib/data/events.json`, so they cannot drift.

Also new: custom `<head>` and per-page OG tags (a page's cover photo becomes its share
card), a real 404 page, and builds that fail loudly on a broken link or a mistyped image
id.

## Nothing runs on a server

`adapter-static` prerenders every route to a plain HTML file. Node is used at build time
only. The `build/` directory is the whole site — deploy it to any static host.

## Commands

```sh
npm install
npm run dev       # regenerates images, then starts the dev server
npm run build     # -> build/   (runs `npm run images` first via prebuild)
npm run preview   # serve build/ locally
npm run images    # regenerate static/images/ from media/
npm run check:calendar   # does the Google Calendar still agree with events.json?
```

## Layout

```
src/
  content/           the pages, as markdown - this is what you edit
    index.md                                 -> /
    about.md                                 -> /about
    artist-area/
      using-obs.md                           -> /artist-area/using-obs
      media-assets/
        media-assets-archive.md              -> /artist-area/media-assets/media-assets-archive
    events/          one file per event, holding only that event's prose
      bms58.md       rendered inside /event-archive by <EventArchive />
  lib/
    components/      Photo, Embed, Columns, Color, PageHeader, NextEvent,
                     EventList, EventArchive, Lineup, AddToCalendar, Nav,
                     Footer, Breadcrumb, Seo
    data/
      events.json    every event, past and upcoming - single source of truth
      nav.json       the main nav, in order
      links.json     socials, Resident Advisor, mailing list, email
      photos.json    per-image alt, caption and photographer credit
      pages.json     GENERATED by the migration - titles for breadcrumbs and routing
      photo-sizes.json  GENERATED by npm run images
    events.js        splits events into upcoming / past / undated
    calendar.js      Google Calendar links and .ics, in Europe/Berlin
  routes/
    +page.svelte     renders content/index.md
    [...path]/       renders everything else, including nested pages
    calendar/[slug].ics/   one prerendered .ics per dated event
media/
  web/               1920px sources scraped from the old site (committed)
  originals/         drop high-res here later; wins automatically. See its README.
scripts/
  build-images.mjs   generates responsive avif/webp/jpg variants
  check-calendar-drift.mjs  compares the Google Calendar against events.json
  migration/         one-shot scripts that pulled the content out of Super
static/images/       GENERATED - gitignored
```

## Editing

### Text

Edit the markdown in `src/content/`. Headings become anchors automatically, so
`## Some Section` is linkable at `#some-section`. Renaming a heading changes its
anchor — if a link to it exists somewhere, update that too.

### Adding an event

One entry at the **top** of `src/lib/data/events.json` — the list runs newest first:

```json
{
  "number": "BMS60",
  "date": "2026-11-14",
  "name": "Winter Patch",
  "venue": "Klunkerkranich",
  "city": "Berlin",
  "url": "https://ra.co/events/...",
  "lineup": [
    { "time": "20:00", "act": "Someone", "url": "https://someone.example" },
    { "time": "21:00", "act": "Someone Else", "instagram": ["someoneelse"] },
    { "time": "22:00", "act": "A b2b B", "instagram": ["a", "b"], "space": "Hinter den Alpen" }
  ],
  "slug": "bms60",
  "hasBody": false
}
```

| Field | |
|---|---|
| `number` | `BMS60`. Also the archive heading and its anchor |
| `date` | `YYYY-MM-DD`, or `null` if genuinely unknown — it then sits at the end of the archive |
| `name` | The event's own name or theme, if it has one. `null` otherwise |
| `url` | Tickets. Shown as a "tickets" link |
| `lineup` | Optional. `space` names the room, and repeats are grouped under one label |
| `lineup[].url` | The act's own site. Makes the act name a link |
| `lineup[].instagram` | A list of handles, for acts with no site of their own. Shown after the name. Two artists sharing a slot get two handles |
| `slug` | Lowercase `number`. The anchor, and the name of the body file |
| `hasBody` | `true` if `src/content/events/<slug>.md` exists |
| `dateDisputed` | Optional note parking a known conflict with the Google Calendar |

Anything dated today or later shows as upcoming; the rest fall into the archive. The
homepage "Next event" box, `/upcoming-dates` and `/event-archive` all read this file,
so they cannot disagree.

The "add to calendar" buttons come from the same record. Start and end times are read
off the running order, and a time earlier than the one before it rolls over midnight —
so a bill ending at 04:00 ends the next morning, not fifteen hours earlier. An event
with no `lineup` gets a 20:00–02:00 placeholder. Everything is converted from
Europe/Berlin wall-clock to UTC, DST included, in `src/lib/calendar.js`. Each dated
event is prerendered to `/calendar/<slug>.ics`, so both buttons are plain links that
work with JavaScript off.

For anything beyond the running order — directions, a DIY kit list, photos, a video —
add `src/content/events/bms60.md` and set `hasBody` to `true`. That file is plain
markdown and can use `<Photo>` and `<Embed>`, so it needs the matching imports:

```svelte
<script>
	import Photo from '$lib/components/Photo.svelte';
</script>

Doors at 19:00. Entrance is through the shopping arcade on Karl-Marx-Strasse.

<Photo id="bms_bms60-flyer" />
```

Its headings start at `####`, because each event already renders under an `<h2>`.

Dates are evaluated at build time, then re-checked in the browser after hydration — so
an event will not sit there stale between deploys. If you want the served HTML itself
always current, schedule a periodic rebuild on your host.

### Where the event data comes from

Two sources of truth, in order:

1. **Facebook**, for BMS1–BMS9 and BMSAV1. Those predate the old Super site — its own
   archive only went back to BMS10 — and Facebook returns HTTP 400 to any logged-out
   request, so they cannot be re-fetched without a session. They live in `POST_FIXES`
   in `scripts/migration/events.py` so a migration re-run cannot wipe them. Facebook is
   authoritative for *dates only*: it renders a venue's **current** name, which is why
   its 2023 entries say "LARK" for what was Marie Antoinette at the time.
2. **The event archive**, for everything else. That is now `events.json`.

**The Google Calendar is not a source of truth.** It is a publishing target: people
subscribed years ago so it has to be kept current, but where it disagrees with
`events.json` the calendar is what is wrong. It went unmaintained for most of 2025 and
was missing BMS56 and BMS59 outright.

### Keeping the Google Calendar in step

```sh
npm run check:calendar
```

It reads the calendar's public `.ics` — no credentials, no write access, nothing that
can touch anyone's subscription — and asks one question: *is the calendar up to date?*

| | |
|---|---|
| upcoming event missing from Google | **fails** — subscribers cannot see it |
| upcoming event on the wrong date | **fails** — subscribers turn up on the wrong night |
| past event on the wrong date | printed only; the calendar's history is not worth backfilling |
| embed no longer points at the checked calendar | **fails** |

Only *upcoming* events have to be present: the calendar starts in late 2022, so
requiring the whole archive would report the same two dozen gaps forever.

`.github/workflows/calendar-drift.yml` runs it on every change to `events.json`, and
weekly. It is deliberately separate from the deploy workflow — a stale Google calendar
is no reason to stop publishing the site, so it only sends you a failure notification.

Fix what it reports **in Google Calendar**, not in `events.json` — the archive is the
source of truth, so only change it if the archive itself turns out to be wrong.

### Adding a photo

Filenames carry the rights holder as a prefix: `<rights-holder>_<description>.<ext>`.
Use `bms_` for BMS's own photos, flyers and artwork, a slugified name for anyone else's,
or `unknown_` if you genuinely do not know. See [COPYRIGHT.md](COPYRIGHT.md).

1. Put the file in `media/web/` (or `media/originals/` if it's high-res), named with the
   id you want, e.g. `bms_bms60-flyer.jpg`.
2. Add an entry to `src/lib/data/photos.json`, keyed by the id:
   ```json
   "bms_bms60-flyer": {
     "id": "bms_bms60-flyer",
     "file": "bms_bms60-flyer.jpg",
     "alt": "BMS60 flyer, listing the running order",
     "caption": "BMS60 at Klunkerkranich",
     "captionHtml": "BMS60 at Klunkerkranich",
     "credit": null,
     "creditUrl": null
   }
   ```
   Set `credit` whenever someone else took it — it renders under the photo.
3. Reference it: `<Photo id="bms_bms60-flyer" />`
4. `npm run images`

A `<Photo>` with an unknown id fails the build rather than shipping a broken image.

### Page header

A page's banner and logo come from its frontmatter, and both are ordinary photo ids:

```yaml
---
title: "Berlin Modular Society"
cover: "bms_dsc-1652-2-crop-banner"
icon: "bms_logo-in-black-on-white-background"
---
```

Both are optional. `cover` also becomes that page's OG share image.

### Colour

Notion let you colour a word or a paragraph, and BMS used it on `/artist-area` and in
parts of the archive. The colours are kept under Notion's own names:

```md
Inline is a plain span: Where: <span class="nc-blue">FITZROY</span>, Berlin.
```

```svelte
<Color c="orange">

A whole coloured paragraph, with **bold** and [links](/submit) still working.

</Color>
```

Use `<Color>` rather than a `<span>` for a whole block. mdsvex stops parsing markdown
inside a line that opens with a tag, so a span wrapped round a paragraph leaves the
`**bold**` and `[links](/x)` as literal text — the component form avoids that. The nine
names are `nc-gray`, `nc-brown`, `nc-orange`, `nc-yellow`, `nc-green`, `nc-blue`,
`nc-purple`, `nc-pink` and `nc-red`, defined in `src/app.css` for light and dark.

### Embeds

`<Embed src="https://www.youtube.com/embed/..." />` — YouTube, SoundCloud, Bandcamp,
Mixcloud and Google Calendar/Forms all work. Audio players get a fixed height, video gets
16:9.

## Known gaps from the migration

Worth a pass by someone who was there, none of it blocking:

- **8 events have no date.** BMS2, 3, 4, 6, 7, 8, 9 and BMSAV1 were bare headings on the
  old site. They render at the end of the archive as "date not recorded".
- **17 events have an inferred year.** The archive usually gave "Thursday 7th March"
  and no year. Those carry `"inferredYear": true` in `events.json` — search for it and
  confirm against your own records. Spot-checking BMS41 through BMS46 is the best use
  of five minutes here, as that run had no stated year at all.
- **BMS51 is missing.** The old archive says "(BMS51 skpped so far)".
- **BMS55 appears twice in the Google Calendar's history.** It has "BMS55 @ Neulant"
  on 19 July 2025 — a one-hour entry against a 5.8h median, never edited after it was
  created in February, so it reads as a pencilled hold that did not go ahead. The
  archive's 25 September 2025 at Klunkerkranich is the event, and stands.
- **1 of 87 photos have no alt text.** Notion set every alt to the literal word "image", so
  alt is derived from the filename where the filename says something (`bms_obs-general-settings`
  → "OBS general settings"). The `IMG_####` ones from `/community` could not be, and are
  empty. Grep `"alt": ""` in `photos.json`.
- **No photographer credits.** Nothing on the Super site recorded one, so every
  `credit` is `null`. See [COPYRIGHT.md](COPYRIGHT.md).

## Deploying

Build command `npm run build`, publish directory `build`.

Keep the existing URLs. All 17 slugs from the Super site are preserved, including the
nested `/artist-area/media-assets/media-assets-archive`.

### GitHub Pages (configured)

`.github/workflows/deploy.yml` builds on every push to `main` and publishes `build/` as a
Pages artifact. **Do not use a `docs/` folder** — that is the older deploy-from-branch
method and would mean committing 45 MB of generated images on every content change.
`build/` and `static/images/` stay gitignored.

One-time setup: **Settings → Pages → Source → GitHub Actions**. Then push to `main`.

Three files exist purely for Pages, and the site breaks without them:

| File | Why |
|---|---|
| `static/.nojekyll` | Without it Jekyll strips `_app/` — the leading underscore — and every stylesheet and script 404s |
| `static/CNAME` | The custom domain. Delete this file if you are not using one |
| `build/404.html` | Generated by `adapter: adapter({ fallback: '404.html' })`. Pages serves it for unknown paths, and it boots the app so `+error.svelte` renders |

The workflow caches `static/images/`, keyed on the contents of `media/`. Without that,
every deploy re-encodes 387 image variants with sharp, which dominates the build time.
Change a photo and only that photo is re-encoded.

`workflow_dispatch` is enabled so you can rebuild from the Actions tab without pushing —
useful because event dates are evaluated at build time.

### Pointing berlinmodularsociety.com at it

The `CNAME` file only tells GitHub which domain to answer for. You still have to move DNS
off Super. For an apex domain, replace the existing records with GitHub's Pages A/AAAA
records (confirm the current values in GitHub's "Managing a custom domain" docs before
changing anything), then tick **Enforce HTTPS** in Settings → Pages once the certificate
is issued. That is the actual cutover from the Super site — do it last, once you have
checked the Pages URL.

### If you deploy to a project path instead

Serving from `username.github.io/BerlinModularSociety` rather than a custom domain needs
`kit.paths.base`, which `svelte.config.js` already reads from `BASE_PATH` and the
workflow already sets. Every absolute path in the project has to be prefixed with it —
the nav, footer, breadcrumb, favicon and the `/images/...` srcsets in `Photo.svelte` all
are. Check the two internal links inside the markdown if you go this route.

### Alternatives

Cloudflare Pages and Netlify take the same `npm run build` / `build` pair. They give you
control over cache headers and, on Cloudflare, on-the-fly image resizing. Neither is
necessary — the responsive variants are pre-generated.

## Images

`npm run images` reads each source once and writes AVIF, WebP and a JPEG/PNG fallback at
640 / 1280 / 1920px, plus the intrinsic dimensions into `photo-sizes.json` so every
`<img>` ships `width`/`height` and never causes layout shift.

Generated files are gitignored. Only the sources in `media/` are committed.
